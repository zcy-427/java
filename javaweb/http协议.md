### 交互的方式
- 请求：永远都是客户端向服务端发送
- 响应：永远都是服务端相客服端返回

### 数据的格式
- 请求时发送的数据，称之为请求报文
- 响应时返回的数据，称之为响应报文

### 报文的格式

#### A. 请求报文 (Request Message)

请求报文由四个部分组成：

1. **请求行 (Request Line)**：包含 请求方法、请求URL、HTTP版本。（如 GET /index.html HTTP/1.1）
    
2. **请求头 (Headers)**：以键值对的形式传递客户端的附加信息。（如 Host: www.example.com, User-Agent: Mozilla/5.0）
	
    
3. **空行 (Blank Line)**：一个只包含回车换行符（CRLF）的空行，用于分隔头部和主体。
    
4. **请求体 (Body)**：实际要发送给服务器的数据（GET请求通常没有请求体，POST请求一般有，如表单数据或JSON）。
    


> [!NOTE] 常见的请求头
> -主机虚拟地址
Host:localhost:8080
-长连接
Connection:keep-alive
-请求协议的自动升级[http的请求，服务器却是nttps的，浏览器自动会将请求协议升级为nttps的]
Upgrade-Insecure-Requests:1
-用户系统信息
User-Agent:Mozilla/5.0 (Windows NT 6.1;WOW64)AppleWebKit/537.36 (KHTML,like Gecko)Chrome/68.0.3440.75 Safari/537.36
-浏览器支持的文件类型
Accept text/html,application/xhtml+xml,application/xml;q=0.9,image/webp,image/apng,*/*;q=0.8
-当前页面的上一个页面的路径[当前页面通过哪个页面跳转过来的]：
可以通过此路径跳转回上一个页面，广告计费，防止盗链
Referer:http://localhost:8080/05_web_tomcat/login.html
-浏览器支持的压缩格式
Accept-Encoding:gzip,deflate,br
-浏览器支持的语言
Accept-Language:zh-CN,zh;q=0.9,en-US;q=0.8,en;q=0.7

#### B. 响应报文 (Response Message)

响应报文也由四个部分组成：

1. **状态行 (Status Line)**：包含 HTTP版本、状态码、状态描述。（如 HTTP/1.1 200 OK）
    
2. **响应头 (Headers)**：服务端传递的附加信息。（如 Content-Type: text/html, Server: nginx）
    
3. **空行 (Blank Line)**：与请求报文相同，用于分隔。
    
4. **响应体 (Body)**：服务器返回给客户端的实际内容（如 HTML 文档或 JSON 数据）

### 长连接与短连接问题

#### 长连接
- **工作模式**：建立连接 -> 传输数据 -> 关闭连接。
    
- **在 HTTP 中的体现**：HTTP/1.0 默认使用短连接。客户端每发一次请求，都需要和服务器进行一次 TCP 的“三次握手”，请求结束后立刻“四次挥手”断开连接。
    
- **优点**：管理简单，服务器不需要维持大量空闲的连接状态，节省服务器内存和连接数资源。
    
- **缺点**：每次请求都要重新建立 TCP 连接，极其耗费时间和网络资源（高延迟）。现在的网页通常包含几十上百个图片、JS、CSS 文件，如果全用短连接，页面加载会非常慢。

#### 短连接
- **工作模式**：建立连接 -> 传输数据 -> **保持连接不断开** -> 再次传输数据 -> ... -> 直到一方主动关闭或超时才关闭连接。
    
- **在 HTTP 中的体现**：HTTP/1.1 起默认开启长连接。在请求头中通常带有 Connection: keep-alive。
    
- **优点**：省去了频繁建立和断开连接的开销，极大地降低了延迟，提高了网络吞吐量。
    
- **缺点**：如果连接一直保持但又没有数据传输（空闲状态），会白白占用服务器的端口和内存资源。
    
- **解决办法**：服务器通常会设置一个**超时时间（Timeout）**和**最大请求数**。例如，如果一条长连接 60 秒内没有新请求，或者复用了 100 次，服务器就会主动断开它。另外，像 WebSocket 这种真正的持久长连接，通常需要通过**心跳包（Heartbeat）**来维持，证明双方“还活着”。

### 3次握手与4次挥手

TCP 报文中的核心标志位（Flag）：

- **SYN (Synchronize)**：用于发起连接，同步序列号。
    
- **ACK (Acknowledgment)**：用于确认收到了对方的数据或请求。
    
- **FIN (Finish)**：用于结束连接，表示发送方没有数据要发送了。
    
- **seq (Sequence Number)**：序列号，用来标识发送的数据字节流。
    
- **ack (Acknowledgment Number)**：确认号，期望收到对方下一个报文的序列号（通常是收到的 seq + 1）。

#### 3次握手(建立连接)

假设客户端发起连接：

- **第一次握手（客户端 -> 服务端）**：  
    客户端发送一个带有 SYN=1 标志的报文，并随机生成一个初始序列号 seq = x。  
    (客户端状态：进入 SYN_SENT 状态)
    
**潜台词**：客户端：“喂，能听到吗？我想和你建立连接，我的初始暗号是 x。”

- **第二次握手（服务端 -> 客户端）**：  
    服务端收到 SYN 报文后，确认客户端的发送能力正常。服务端需要发送一个带有 SYN=1 和 ACK=1 标志的报文。同时随机生成自己的初始序列号 seq = y，并确认客户端的序列号 ack = x + 1。  
    (服务端状态：进入 SYN_RCVD 状态)
    
 **潜台词**：服务端：“听到了！我同意建立连接，我的暗号是 y，你刚才的暗号 x 我收到了（所以期待你下次发 x+1）。”

- **第三次握手（客户端 -> 服务端）**：  
    客户端收到服务端的 SYN+ACK 报文后，确认服务端的发送和接收能力正常。客户端再发送一个带有 ACK=1 标志的报文，seq = x + 1，ack = y + 1。  
    (双方状态：都进入 ESTABLISHED 状态，连接建立成功！)
    
**潜台词**：客户端：“收到你的确认了！你的暗号 y 我也收到了。咱们开始传数据吧！”

#### 4次挥手(断开连接)

假设还是客户端主动发起关闭：

- **第一次挥手（客户端 -> 服务端）**：  
    客户端数据发完了，发送一个带有 FIN=1 标志的报文，序列号 seq = u。  
    (客户端状态：进入 FIN_WAIT_1 状态)
    
**潜台词**：客户端：“我这边的数据全都发完了，我要关闭发送通道了。”（但此时客户端还能**接收**数据）


- **第二次挥手（服务端 -> 客户端）**：  
    服务端收到 FIN 报文，立刻回复一个 ACK=1 的报文，ack = u + 1。  
    (服务端状态：进入 CLOSE_WAIT 状态；客户端收到后进入 FIN_WAIT_2 状态)
    
 **潜台词**：服务端：“收到你的关闭请求了。但我这里可能还有点数据没传完，你等我发完。”（此时客户端到服务端的通道关闭，进入**半关闭状态**）

- **第三次挥手（服务端 -> 客户端）**：  
    服务端把剩下的数据都发送完毕后，也发送一个带有 FIN=1 的报文，序列号 seq = w。  
    (服务端状态：进入 LAST_ACK 状态)
    
**潜台词**：服务端：“我这边的数据也全都发完了，我也可以关闭连接了。”

- **第四次挥手（客户端 -> 服务端）**：  
    客户端收到 FIN 报文后，回复一个带有 ACK=1 的报文，ack = w + 1。  
    (服务端收到后进入 CLOSED 状态，连接彻底断开)  
    (客户端发出后进入 TIME_WAIT 状态，等待 **2MSL** 的时间后，才进入 CLOSED 状态)
    
 **潜台词**：客户端：“好的，知道了，再见！”


> [!NOTE] 为什么还要等待2MSL才关闭
> MSL 指报文在网络中的最长存活时间，2MSL 大约是 1 到 4 分钟
> 1. **保证服务端能够成功收到最后一个 ACK**：如果客户端发送的最后那个 ACK 丢包了，服务端没收到，就会以为客户端没收到自己的 FIN，从而重发 FIN。如果客户端不等待直接关闭了，就无法回复重发的 FIN，服务端就会一直无法正常关闭。客户端等一会儿，就是为了处理这种重传情况。
> 2. **防止“旧连接”的报文干扰“新连接”**：等 2MSL 可以确保这个连接内产生的所有网络报文都在网络中自然消亡（过期）。这样下次用同一个端口建立新连接时，就不会收到上一次连接残留的“幽灵数据包”。
